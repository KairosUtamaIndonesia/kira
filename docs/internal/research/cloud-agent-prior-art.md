# Cloud coding agents: prior art for Kira

**Question:** How do mature products that run coding agents in remote sandboxes shape the product and the protocol around them, and what does that mean for Kira's seams (pi `*Operations`, `Conversation`, `openChats.ts`, the `/v1` proxy and keys, no server-side transcript)?

**Researched:** 2026-10-06, from vendor docs, changelog-style pages, open-source code and vendor engineering posts. Every claim carries its source. Anything the sources do not say is marked **UNVERIFIED**.

## Conclusion

1. **"Where does the loop run" has four answers, and every serious vendor ships at least two.** A: loop and tools together in the sandbox. B: loop in the vendor cloud, tools in a sandbox the vendor or the customer runs. C: loop on your machine, tools routed to a remote executor. D: loop on your own machine, with phone/web as a thin remote client. Kira today is D (ADR 0012/0024) with a local-only client.
2. **The sandbox never holds the real credential** is the one rule all of them converge on, and they got there by being burned. Anthropic says the coupled design let a prompt injection "read its own environment"; Codex moved from "secrets deleted before the agent phase" to proxy-substituted placeholders; pi's own containerization docs list the same two proxy tricks.
3. **The transcript lives outside the sandbox.** Anthropic's engineering post, the Agent SDK hosting guide, OpenCode v2 and Cursor all make the session log a separate durable thing. A sandbox that dies loses its filesystem and background processes, never the conversation.
4. **Steer/stop/resume over a bad link reduce to: a durable, sequence-numbered log plus idempotent admission.** Live token deltas are best-effort and never the record.
5. **One task = one sandbox = one branch = one PR, triggered and paid for by one person.** Nobody maps a ticket to a shared long-lived runner.
6. **Decision this forces for Kira:** is the goal *hands remote* (isolation, parallel checkouts, heavy builds) or *the run outlives the laptop*? The first is a small change at pi's `*Operations` seam and keeps Kira's model-key, SQLite and no-server-transcript properties. The second moves the loop off the desktop and reopens ADR 0012/0024/0028 and the transcript question. See "Implications for Kira".

## The four placements

| | Loop (the "brain") | Tools (the "hands") | Who ships it |
| --- | --- | --- | --- |
| **A. Brain in sandbox** | next to the tools | same sandbox | Claude Code on the web, Cursor Cloud Agents (managed), Copilot cloud agent, Codex Cloud*, OpenHands V1 agent-server, OpenHands/pi "whole process in a container" |
| **B. Brain in vendor cloud, hands in a sandbox** | vendor cloud | vendor sandbox or customer worker over outbound HTTPS | Anthropic Managed Agents (+ self-hosted sandboxes), Cursor Self-Hosted Machines, Devin (brain always in Cognition's cloud) |
| **C. Brain local, hands remote** | your process | remote executor over RPC | Codex `exec-server`, pi `*Operations` (ssh, Gondolin), OpenHands V0 runtime |
| **D. Brain on your machine, thin remote client** | your laptop/desktop | same machine | Codex Remote, Copilot CLI remote control, Claude Remote Control, Vibe Kanban remote access |

\* Codex Cloud's loop location is not stated in the docs I read (**UNVERIFIED**); "the agent runs terminal commands in a loop" inside the container is as far as they go ([legacy environments](https://developers.openai.com/codex/cloud/environments)).

## Per product

Numbers refer to the seven questions: (1) loop placement, (2) repo in / changes out, (3) secrets and model credential, (4) transcript stream, steer/stop/resume, (5) environment setup and network, (6) ticket to run mapping and billing, (7) documented failure modes.

### OpenAI Codex (cloud, app-server, exec-server, SDK, Remote)

1. **Loop.** Cloud: container runs "the agent … terminal commands in a loop" ([cloud environments, legacy](https://developers.openai.com/codex/cloud/environments)); where model inference is called from is **UNVERIFIED**. Separately Codex ships a brain-local/hands-remote protocol: `codex exec-server` is "a small JSON-RPC server for spawning and controlling subprocesses" plus filesystem RPCs (`process/start`, `process/read`, `process/write`, `process/terminate`, `fs/*`), driven by a harness that lives elsewhere ([exec-server README](https://github.com/openai/codex/blob/main/codex-rs/exec-server/README.md)). The app server can point at "a configured execution environment" via `environment/info` ([app-server](https://developers.openai.com/codex/app-server)). Codex Remote is pattern D: "Codex runs each task on your connected computer" and the phone "sends prompts, approvals, and follow-up messages" ([Remote](https://developers.openai.com/codex/remote), [remote connections](https://learn.chatgpt.com/docs/remote-connections)).
2. **Repo.** GitHub connection; the container "checks out your repo at the selected branch or commit SHA"; when done "you can open a PR" ([legacy environments](https://developers.openai.com/codex/cloud/environments)). GitLab and GHES are listed as unsupported in cloud ([cloud environments](https://developers.openai.com/codex/environments/cloud-environments)).
3. **Secrets.** Legacy: secrets "are only available to setup scripts … removed before the agent phase" ([legacy environments](https://developers.openai.com/codex/cloud/environments)). Current: a *network secret* is a placeholder in the sandbox; "the proxy substitutes the real value for allowed destinations", HTTPS port 443 only, and "doesn't put the raw credential in a local process or file" ([cloud environments](https://developers.openai.com/codex/environments/cloud-environments)). Personal vault values are per-user; sharing an environment "shares these requirements, not your personal credentials" (same page). OIDC short-lived tokens are available by request for Enterprise (same page). The model credential in cloud is not described (**UNVERIFIED**).
4. **Stream, steer, resume.** App-server threads are `thread/start|resume|fork`; `turn/steer` "append[s] user input to the active in-flight turn" and requires `expectedTurnId`; `turn/interrupt` ends the turn as `interrupted`; `thread/unsubscribe` keeps a thread loaded for 30 minutes of inactivity ([app-server](https://developers.openai.com/codex/app-server)). The exec-server relay has an explicit reliability layer: per-stream `seq`, cumulative `ack` plus `ack_bits`, `resume`, `reset`, `heartbeat`, and "the existing harness reconnect flow can then resume a retained destination session"; "recovery is limited by the destination's session and process-output retention" ([exec-server README](https://github.com/openai/codex/blob/main/codex-rs/exec-server/README.md)). If the websocket closes, "the server terminates any remaining managed processes for that client connection" (same page, lifecycle). Cloud tasks: "Reopen the same task to continue its work across devices" ([cloud environments](https://developers.openai.com/codex/environments/cloud-environments)). The cloud task stream protocol is not public in what I read (**UNVERIFIED**).
5. **Environment.** "Install script" plus a "Start skill" (instructions to start services), tested interactively, then **Published**; publishing "captures the prepared filesystem for new tasks"; an existing task "continues with its own saved files, including uncommitted changes"; saved VM state is recoverable up to seven days; "Saved state doesn't replace source control" ([cloud environments](https://developers.openai.com/codex/environments/cloud-environments)). Network: legacy default is off in the agent phase with a domain allowlist and a method restriction to GET/HEAD/OPTIONS ([internet access](https://developers.openai.com/codex/cloud/internet-access)); current has a "Package managers" preset and "All (unrestricted)". The repo-declared secure devcontainer is for *local* use ([security](https://developers.openai.com/codex/agent-approvals-security)).
6. **Tickets.** Assign a Linear issue to Codex or `@Codex` it: "Codex creates a cloud chat and replies with progress"; follow-ups in the thread "continue the same chat"; triage rules run chats "using the account of the issue creator" ([Linear](https://developers.openai.com/codex/third-party/linear)). In Slack, "another participant's request doesn't automatically continue your task" ([cloud environments](https://developers.openai.com/codex/environments/cloud-environments)). VM size depends on the ChatGPT plan ([same page](https://developers.openai.com/codex/environments/cloud-environments)); how cloud tasks are metered is not stated there (**UNVERIFIED**).
7. **Failure modes.** Prompt injection via an issue body that makes the agent `curl` data out, spelled out with an example ([internet access](https://developers.openai.com/codex/cloud/internet-access)). Safety monitoring can pause a task after the triggering activity ([security](https://developers.openai.com/codex/agent-approvals-security)). Exec-server: "Non-loopback WebSocket listeners currently allow unauthenticated connections by default during rollout" ([app-server](https://developers.openai.com/codex/app-server)).

### Claude Code on the web, Agent SDK hosting, Managed Agents

1. **Loop.** Cloud sessions are pattern A: "a Claude Code session that runs on cloud infrastructure"; with network access off "Claude Code can still communicate with the Anthropic API, which may allow data to exit the VM", i.e. the loop is in the VM ([Claude Code on the web](https://code.claude.com/docs/en/claude-code-on-the-web)). The Agent SDK is also A: "spawns and supervises a `claude` CLI subprocess that owns a shell, a working directory, and session files on disk" ([hosting](https://code.claude.com/docs/en/agent-sdk/hosting)). **Managed Agents is pattern B and the clearest statement of the fork**: "decouple … the 'brain' (Claude and its harness) from … the 'hands' (sandboxes and tools) and the 'session' (the log of session events)"; the harness "called the container the way it called any other tool: `execute(name, input) → string`" ([engineering post](https://www.anthropic.com/engineering/managed-agents)). Self-hosted sandboxes keep "orchestration on Anthropic's side but move tool execution into infrastructure you control" via an outbound-only worker polling a work queue ([self-hosted sandboxes](https://platform.claude.com/docs/en/managed-agents/self-hosted-sandboxes)). Remote Control is pattern D ([web docs](https://code.claude.com/docs/en/claude-code-on-the-web)).
2. **Repo in / out.** GitHub App, or `/web-setup` which sends the local `gh` token to your account; branches are pushed back. With no remote, or no App installed, the CLI **uploads a git bundle** (history of all branches plus uncommitted changes to tracked files, under 100 MB, falling back to current-branch bundle then a squashed snapshot); uncommitted `.env`, `*.tfvars`, `*.pem`, `id_rsa` changes are left out ([web docs](https://code.claude.com/docs/en/claude-code-on-the-web)). A bundled session can push back "only when your GitHub connection has push access". GitLab/Bitbucket: bundle only, "can't push results back" (same page). All GitHub traffic goes through a proxy; the VM holds a "scoped credential, which the proxy verifies and swaps for your actual GitHub token"; the proxy "rejects branch deletions and pushes of anything other than a branch" but "doesn't limit which branches a push can update" ([cloud environments](https://code.claude.com/docs/en/cloud-environments#github-proxy)). Commits carry a `Claude-Session: <url>` trailer and PR bodies link the session (same page).
3. **Secrets and model credential.** "Your GitHub credentials stay encrypted on Anthropic's servers and never enter a session's VM" ([web docs](https://code.claude.com/docs/en/claude-code-on-the-web)). User API keys stored as environment *API credentials* are attached by the proxy "after each request leaves the session's VM … The key never reaches Claude, the commands it runs, or the session's environment variables" (Pro/Max only, not Team/Enterprise; [cloud environments](https://code.claude.com/docs/en/cloud-environments#add-api-credentials)). Plain environment variables "anyone who uses the environment can read" (same page). The model credential inside a cloud VM is not described (**UNVERIFIED**). For self-hosting the SDK, the documented pattern is `ANTHROPIC_BASE_URL` pointing at "a proxy that injects the key outside the container" ([hosting](https://code.claude.com/docs/en/agent-sdk/hosting), [secure deployment](https://code.claude.com/docs/en/agent-sdk/secure-deployment)). In Managed Agents the structural fix is "make sure the tokens are never reachable from the sandbox where Claude's generated code runs": git tokens wired into the remote at clone time, MCP OAuth tokens in a vault behind a proxy ([engineering post](https://www.anthropic.com/engineering/managed-agents)).
4. **Stream, steer, resume.** Managed Agents: `user.message` / `user.interrupt` events in, SSE out; the send call "returns as soon as the events are queued" and an interrupt's `processed_at` "stays null until the agent applies it"; "Only events emitted after the stream is opened are delivered, so open the stream before sending"; reconnect = open stream, list full history, dedupe by event id, tail; live text deltas are opt-in per connection and "the buffered `agent.message` is always the authoritative record" ([events and streaming](https://platform.claude.com/docs/en/managed-agents/events-and-streaming)). Claude Code web: follow-ups can be queued from any machine with `claude -p "…" --cloud <id>`, which "exits without waiting for a reply"; a queued message can be taken back with ✕ until Claude reads it; `/clear` does not exist in cloud sessions ([web docs](https://code.claude.com/docs/en/claude-code-on-the-web)). Teleport pulls the session and its branch into a local terminal, but "the terminal gets its own copy … new work there stays local" (same page). Agent SDK transcripts are on container disk and "None of them survive a container restart"; a `SessionStore` adapter *mirrors* them, with "dual-write" and best-effort `mirror_error` messages ([hosting](https://code.claude.com/docs/en/agent-sdk/hosting)). Stopping a self-hosted session is `stopping` then `stopped` after the worker's lease heartbeat notices; `force: true` skips confirmation ([operations](https://platform.claude.com/docs/en/managed-agents/self-hosted-sandboxes-operations)).
5. **Environment.** Environment = network level (None / Trusted / Full / Custom), env vars, setup script as root, filesystem snapshot "reused as the starting point for later sessions" only if setup finishes in "roughly five minutes", rebuilt on script/network change and after ~7 days ([cloud environments](https://code.claude.com/docs/en/cloud-environments)). Sessions stop after idle, VM paused with files saved, later reclaimed ([same page](https://code.claude.com/docs/en/cloud-environments)). Repo-committed `CLAUDE.md`, `.claude/` and `.mcp.json` carry over; user-level config does not (same page). Default VM: 4 vCPU, 16 GB RAM, 30 GB disk (same page). For self-hosted SDK use: 1 GiB RAM, 5 GiB disk, 1 CPU per agent as a floor ([hosting](https://code.claude.com/docs/en/agent-sdk/hosting)).
6. **Tickets and billing.** "Each `--cloud` command creates its own cloud session"; sessions run in parallel; they "share rate limits with all other Claude and Claude Code usage within your account … There is no separate compute charge for the cloud VM" ([web docs](https://code.claude.com/docs/en/claude-code-on-the-web)). A *project* has Claude "start and keep track of" several cloud sessions for one body of work (same page, related resources). Auto-fix subscribes a session to a PR's CI and review events; replies are posted under *your* GitHub account, labelled as Claude Code (same page).
7. **Failure modes.** Environment expired: "Restored: your conversation history. Not restored: background work that was still running … such as subagents and shell commands" ([web docs](https://code.claude.com/docs/en/claude-code-on-the-web)). The coupled-container design made the server a "pet": "if a container failed, the session was lost", and the WebSocket "couldn't tell us where failures arose" ([engineering post](https://www.anthropic.com/engineering/managed-agents)). "No top-level session timeout" in the SDK; set `maxTurns`; no per-subagent wall-clock deadline ([hosting](https://code.claude.com/docs/en/agent-sdk/hosting)). Auto-fix can trigger comment-driven automation such as Atlantis ([web docs](https://code.claude.com/docs/en/claude-code-on-the-web)). A proxy that allowlists by hostname without TLS inspection can be bypassed: "Code running inside the sandbox can potentially use domain fronting or similar techniques to reach hosts outside the allowlist" ([secure deployment](https://code.claude.com/docs/en/agent-sdk/secure-deployment)).

### Cursor Cloud Agents (formerly Background Agents)

1. **Loop.** Managed: "run in isolated VMs … with full development environments"; security overview says "The agent runs code and tools inside the VM and streams its progress, output, and artifacts back" ([cloud agents](https://cursor.com/docs/cloud-agent), [security](https://cursor.com/docs/cloud-agent/security)); whether inference calls originate in the VM is **UNVERIFIED**. **Self-Hosted Machines is pattern B, stated plainly**: "Cursor runs the agent loop, inference, and planning. Your worker performs file edits and terminal commands"; the worker holds "a long-lived outbound HTTPS connection to Cursor's backend, and Cursor sends agent tool calls over that connection"; "No inbound ports, public IPs, or VPN tunnels are required" ([self-hosted](https://cursor.com/docs/cloud-agent/self-hosted)). Workers are `My Machines` (personal) or `Team Pools` ("Chats wait in the team pool until a worker claims them"; one agent per machine; a controller scales capacity; Enterprise plan) (same page).
2. **Repo.** Clone through the Cursor GitHub/GitLab/Bitbucket/Azure DevOps app, work on a separate branch, "push changes to your repo for handoff"; "Access is inherited, never widened" — an agent reaches only repos the triggering user could ([cloud agents](https://cursor.com/docs/cloud-agent), [security](https://cursor.com/docs/cloud-agent/security)). The agent "pushes its branch and opens a draft pull request for a human to review" (security). Every commit is signed with an HSM-backed Ed25519 key ([secrets and network](https://cursor.com/docs/cloud-agent/security-network)). Self-hosted: the checkout "stay[s] on your machine"; an any-repo pool worker clones with `--clone-git-repos` ([self-hosted](https://cursor.com/docs/cloud-agent/self-hosted)).
3. **Secrets.** Three types: *Environment Variable* (visible to the agent), *Runtime Secret* (still an env var, but "redacted from the agent's tool call results, chat transcript, commits" and visible to a human in the Terminal), *Build Secret* (only for the Docker build, never in the running env); OIDC JWTs from a local socket are preferred over long-lived keys ([secrets and network](https://cursor.com/docs/cloud-agent/security-network)). Self-hosted: "Environment-scoped secrets and Build Secrets never reach a worker"; `My Machines` workers "get no dashboard secrets and use the machine's own credentials" ([self-hosted](https://cursor.com/docs/cloud-agent/self-hosted)).
4. **Stream.** Share by URL; viewing is read-only unless an admin enables team follow-ups ([cloud agents](https://cursor.com/docs/cloud-agent)). "Conversation history is kept indefinitely by default … Environment snapshots are stored for a maximum of 90 days of inactivity" ([secrets and network](https://cursor.com/docs/cloud-agent/security-network)). Resume protocol details are not in what I read (**UNVERIFIED**).
5. **Environment.** Agent-led setup, a saved snapshot, or a Dockerfile in `.cursor/environment.json`; "Builds prepare each environment in the background" ([cloud agents](https://cursor.com/docs/cloud-agent)). Network modes: allow all (default: "The agent has internet access by default"), default plus allowlist, allowlist only; settable per user, team, environment; Enterprise can lock it ([secrets and network](https://cursor.com/docs/cloud-agent/security-network)). Self-hosted replaces all of this with "the machine's firewall or HTTPS proxy" and a `sessionStart` hook ([self-hosted](https://cursor.com/docs/cloud-agent/self-hosted)).
6. **Tickets and billing.** Start from Slack, GitHub/Bitbucket comment, Linear, API, iOS, web, desktop; "You can run as many agents as you want in parallel"; "Cloud Agents are charged at API pricing for the selected model" with a spend limit set at first use ([cloud agents](https://cursor.com/docs/cloud-agent)). Self-hosted: "you also pay for and operate your machines" ([self-hosted](https://cursor.com/docs/cloud-agent/self-hosted)).
7. **Failure modes.** "The agent auto-runs all terminal commands … attackers could execute prompt injection attacks, tricking the agent to upload code to malicious websites" ([secrets and network](https://cursor.com/docs/cloud-agent/security-network)). A wildcard `*.s3.us-east-1.amazonaws.com` allowlist entry "creates an exfiltration path for a prompt-injected agent" (same page). Snapshots "can't be deleted on demand" (same page). Self-hosted workers send file contents, terminal output and diffs to Cursor ([self-hosted](https://cursor.com/docs/cloud-agent/self-hosted)).

### GitHub Copilot cloud agent

1. **Loop.** "its own ephemeral development environment, powered by GitHub Actions"; the runner firewall must allow `api.individual|business|enterprise.githubcopilot.com`, which implies the loop (or its inference calls) originates on the runner (inference, not stated outright; [environment](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/customize-the-agent-environment)). So pattern A, with the model endpoint reached from the runner. Copilot CLI remote control is pattern D: "all shell commands, file operations, and tool executions happen on your machine" ([remote control](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/about-remote-control)).
2. **Repo.** Copilot "handles branch creation, commit messages, and pushing changes" ([about](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent)). It can push to **one** branch only (`copilot/…`, or the PR branch on `@copilot` mentions); "It cannot directly run `git push` or other Git commands"; draft PRs only, it "cannot mark its pull requests as 'Ready for review' and cannot approve or merge"; Actions workflows do not run until a human clicks "Approve and run workflows" ([risks and mitigations](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/risks-and-mitigations)). One repo, one branch, one PR per task ([about](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent)). Commits are signed, co-authored by the requester, and link to the session log ([risks](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/risks-and-mitigations)).
3. **Secrets.** "Copilot will be given its own token for its operations" separate from the setup job's `permissions` ([environment](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/customize-the-agent-environment)). A dedicated "Agents" secrets/variables store exists (same page links it; contents not read).
4. **Stream.** Session logs show the work and tools; "you can continue chatting with Copilot about its progress and steer the work"; real-time steering comments each cost a premium request under legacy billing ([about](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent), [legacy billing](https://docs.github.com/en/copilot/concepts/billing/copilot-requests)). Remote-controlled CLI: "Session events … are sent from your local machine to GitHub. Remote commands are polled by Copilot CLI from GitHub and injected into your local session"; "Both the local terminal and the remote interface are active at the same time … uses the first response it receives to any prompt or permission request" ([remote control](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/about-remote-control)).
5. **Environment.** `.github/workflows/copilot-setup-steps.yml`, a normal Actions workflow with a single `copilot-setup-steps` job; only `steps`, `permissions`, `runs-on`, `services`, `snapshot`, `timeout-minutes` (max 59) are honoured; must be on the default branch; "If any setup step fails … Copilot will skip the remaining setup steps and begin working with the current state"; larger or self-hosted ephemeral runners supported ([environment](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/customize-the-agent-environment)). Internet is restricted by a built-in firewall ([risks](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/risks-and-mitigations)).
6. **Tickets and billing.** Start from the agents panel, an issue, a PR, chat; only users with write access can trigger it, and "Comments from users without write access are never presented to the agent"; the requester cannot approve the PR ([risks](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/risks-and-mitigations)). Billing (legacy plans): one premium request per session plus one per steering comment, plus Actions minutes (search-result snippet of the billing overview, page not opened; [legacy billing](https://docs.github.com/en/copilot/concepts/billing/copilot-requests)). GitHub announced a move to usage-based billing on 2026-06-01 ([GitHub blog](https://github.blog/news-insights/company-news/github-copilot-is-moving-to-usage-based-billing/), snippet only; current rates **UNVERIFIED**).
7. **Failure modes.** "Each Copilot cloud agent session has a maximum execution time of 59 minutes … cannot be extended"; a repository ruleset that restricts commit authors can block the agent; hidden characters (HTML comments) are stripped from issue text as an injection mitigation ([about](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent), [risks](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/risks-and-mitigations)). Copilot CLI remote control stops when "the machine goes to sleep or loses its connection" ([remote control](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/about-remote-control)).

### Devin

1. **Loop.** "The Brain: A stateless, cloud-based service … always residing in Cognition's Cloud"; "The Devbox: A secure virtual environment where Devin executes code." On startup the devbox "establishes a secure WebSocket connection to an isolated container in Cognition's tenant" ([deployment](https://docs.devin.ai/enterprise/deployment/overview)). That is pattern B with the customer able to move only the devbox (single-tenant VPC over PrivateLink/IPsec).
2. **Repo.** SCM provider connected per org; repos granted per org by an enterprise admin; devbox must reach SCM and artifact stores ([environment](https://docs.devin.ai/onboard-devin/environment), [deployment](https://docs.devin.ai/enterprise/deployment/overview)).
3. **Secrets.** Org, personal, repo and session scopes; "Devin provides each secret to the specific commands and tools that need it … it binds secrets as environment variables whenever needed" and secrets are "never written into your blueprint or snapshot" ([secrets](https://docs.devin.ai/product-guides/secrets)). Model keys: "Devin … does not currently support third-party LLM API keys" ([deployment](https://docs.devin.ai/enterprise/deployment/overview)), i.e. the model credential is wholly the vendor's.
4. **Stream.** Not documented in what I read (**UNVERIFIED**); the transport is a WebSocket from devbox to brain container ([deployment](https://docs.devin.ai/enterprise/deployment/overview)).
5. **Environment.** "Your environment configuration is saved as a snapshot: a frozen, bootable image that every session starts from"; "Session changes don't persist back to the snapshot"; built from a *blueprint* (YAML Devin proposes for you to approve) ([environment](https://docs.devin.ai/onboard-devin/environment)). "Granting internet access … is strongly recommended" ([deployment](https://docs.devin.ai/enterprise/deployment/overview)).
6. **Tickets.** "Split tasks into verifiable sub-tasks, and start one Devin session for each sub-task"; success criteria and checkpoints per session; usage in ACUs ([instructing Devin](https://docs.devin.ai/essential-guidelines/instructing-devin-effectively)).
7. **Failure modes.** Docs warn that vague scope makes Devin "get stuck" and to avoid "Improve our database's performance" style tasks ([instructing Devin](https://docs.devin.ai/essential-guidelines/instructing-devin-effectively)). MFA VPNs are incompatible with the multi-tenant cloud ([deployment](https://docs.devin.ai/enterprise/deployment/overview)).

### OpenHands (open source)

1. **Loop: it moved.** V0: backend spawns the `Agent` and an `EventStream`; an **Action Executor** inside the Docker container receives actions "over RESTful API" and returns observations — brain outside, hands inside (pattern C/B) ([runtime architecture](https://docs.openhands.dev/openhands/usage/architecture/runtime)). V1 names this a mistake: "Every tool call in V0 executed in a sandboxed Docker container by default … the agent and sandbox ran as separate processes, states diverged easily, and multi-tenant workloads could crash each other"; principle: "Sandboxing should be opt-in, not universal" and the agent server "runs inside sandbox" ([design principles](https://docs.openhands.dev/sdk/arch/design)). In V1 the **Agent Server** (FastAPI, REST plus WebSocket) runs the SDK *inside* the workspace; clients are thin; "Tools run alongside the agent … They don't run 'through' workspace APIs" ([SDK overview](https://docs.openhands.dev/sdk/arch/overview), [remote server](https://docs.openhands.dev/sdk/guides/agent-server/overview)). Same `Conversation` code works with `LocalWorkspace`, `DockerWorkspace`, `RemoteAPIWorkspace`; swapping the workspace turns it into a `RemoteConversation` (same pages).
2. **Repo.** Workspace-specific; the docs show file upload/download and `execute_command` through the server ([remote server](https://docs.openhands.dev/sdk/guides/agent-server/overview)). Git flow not read (**UNVERIFIED**).
3. **Secrets.** The documented client example passes `LLM(api_key=SecretStr(...))` into the conversation sent to the agent server, and "`OH_SECRET_KEY` encrypts sensitive values stored with conversations, including LLM API keys and secrets" ([agent server](https://docs.openhands.dev/sdk/arch/agent-server)). So in the documented setup the sandbox-side server holds the real LLM key. The server "starts without API authentication" by default and "Do not expose an unauthenticated Agent Server on a public network" (same page); auth is `X-Session-API-Key`.
4. **Stream.** WebSocket event streaming, typed events, "deterministic replay" from a single mutable conversation state ([remote server](https://docs.openhands.dev/sdk/guides/agent-server/overview), [design](https://docs.openhands.dev/sdk/arch/design)). Reconnect cursor semantics **UNVERIFIED**.
5. **Environment.** Docker image built per base image with source/lock/version tags so unchanged inputs reuse a layer ([runtime architecture](https://docs.openhands.dev/openhands/usage/architecture/runtime)).
7. **Failure modes.** V0: failed session restores and silent state inconsistencies from mutable Python objects ([design](https://docs.openhands.dev/sdk/arch/design)).

### OpenCode (server/client split, as used by OpenChamber)

1. **Loop.** In the server. "When you run `opencode` it starts a TUI and a server. Where the TUI is the client"; `opencode serve` is the headless form; web, IDE and desktop are other clients ([server](https://opencode.ai/docs/server/)). So pattern A/D-shaped: the loop and tools are co-located in the server process; remote means "point a client at a server". v2 adds `Location` with a reserved `workspaceID`: "An omitted `Location.workspaceID` means implicit-local placement; explicit workspace identity remains reserved for future placement semantics" ([v2 session spec](https://github.com/anomalyco/opencode/blob/dev/specs/v2/session.md)).
2. **Repo.** Server sees its own filesystem; `/vcs`, `/file`, `/session/:id/diff`, and v2 `worktree` routes expose it ([server](https://opencode.ai/docs/server/), [v2 API](https://opencode.ai/v2/docs/api)).
3. **Secrets.** Provider credentials are server-side: `PUT /auth/:id` sets them, and v2 has `credential` and `integration` resources including OAuth attempts ([server](https://opencode.ai/docs/server/), [v2 API](https://opencode.ai/v2/docs/api)). Auth to the server is HTTP basic via `OPENCODE_SERVER_PASSWORD`; v2 adds one-time pairing codes (`POST /api/pair`, `GET /auth/connect/{code}`) (same pages).
4. **Stream, steer, resume. The most relevant protocol.** v1: `GET /event` is SSE, "first event is `server.connected`"; `POST /session/:id/prompt_async` returns 204; `POST /session/:id/abort`; no resume cursor documented ([server](https://opencode.ai/docs/server/)). v2 is a redesign: `sessions.prompt` writes a **durable inbox row** (`PromptAdmitted`) with caller-supplied message ID — "exact reuse returns the same admission receipt" (idempotent retry) — and execution is a separate step; `delivery` is `steer` ("promote at the next safe provider-turn boundary") or `queue` (FIFO, "exactly one queued input" when otherwise idle); inbox items can be listed, edited, cancelled; `sessions.events({ sessionID, after? })` replays durable events after an aggregate sequence cursor then tails "without a race"; live text/reasoning/tool-input deltas "remain available through EventV2 subscriptions … intentionally absent from the replayable Session stream" and "cannot advance the durable cursor"; interrupt "preserves durable inbox rows for a later wake"; after a process restart a tool still projected `running` "durably fail[s] … `Tool execution interrupted`; abandoned side effects are never silently replayed"; "Post-crash continuation recovery is intentionally deferred" and "clustered Session execution ownership and stale-runtime fencing" are listed as follow-ups ([v2 session spec](https://github.com/anomalyco/opencode/blob/dev/specs/v2/session.md)). The v2 event stream itself is "Volatile by contract: a slow consumer overflows and fails the stream, and events during disconnection are missed" ([v2 API search result](https://opencode.ai/v2/docs/api), snippet); the durable log is the recovery path. The v2 event schemas "remain experimental and unshipped" (spec).
5. **Environment.** None beyond the host; `PUT /api/session/{id}/environment` sets per-session env ([v2 API](https://opencode.ai/v2/docs/api)).
6. **Tickets.** Sessions can have `parentID`, `/session/:id/children`: subagents are child sessions ([server](https://opencode.ai/docs/server/)); no ticket concept.
7. **Failure modes.** v2 `bash` "is not sandboxed: the spawned shell runs with the host user's filesystem, process, and network authority" ([v2 session spec](https://github.com/anomalyco/opencode/blob/dev/specs/v2/session.md)). An unauthenticated `opencode serve` is arbitrary command execution on that host (inference from the API: `POST /session/:id/shell`).

### Vibe Kanban and similar kanban-on-agents tools

1. **Loop.** On the host. There is a "Vibe Kanban Cloud" (self-hostable) while agents run on a host device; Remote Access lets another device reach "a host instance" by pairing it with a code ([remote access](https://vibekanban.com/docs/remote-access), [README](https://github.com/BloopAI/vibe-kanban/blob/main/README.md)). That is exactly Kira's shape: server owns the board, desktops run the agent. The README's env table has `VK_TUNNEL` / `VK_SHARED_RELAY_API_BASE` for relay mode (same README).
2. **Repo.** "Vibe Kanban uses Git worktrees to create isolated environments for each task attempt. These environments are ephemeral and automatically cleaned up" ([monitoring task execution](https://vibekanban.com/docs/core-features/monitoring-task-execution)). PRs created and merged on GitHub (README).
4. **Stream.** Real-time logs per attempt; approvals "currently supported for Codex" only; message edit "will revert the agent's work to that point and replay"; processes view for agent sessions and dev servers ([monitoring](https://vibekanban.com/docs/core-features/monitoring-task-execution)).
5. **Environment.** Per-project setup script runs in each new worktree; a cleanup script runs after every agent turn (same page).
6. **Tickets.** Issue → workspace → agent attempt; several attempts per task are visible ("View all task attempts"); parallel workspaces (same page, README).
7. **Caution.** The README begins "Vibe Kanban is sunsetting" ([README](https://github.com/BloopAI/vibe-kanban/blob/main/README.md)). Use it as a design reference only.

### pi itself (the harness Kira runs)

pi documents both patterns Kira would choose between: "run the whole `pi` process inside an isolated environment, or run `pi` on the host and route tool execution into an isolated environment" ([containerization](../../../apps/desktop/node_modules/@earendil-works/pi-coding-agent/docs/containerization.md)).

- **Hands remote:** the Gondolin example "overrides `read`, `write`, `edit`, `bash`, `grep`, `find`, and `ls`" and routes user `!` commands too, "keeping auth on host" (same page, [example](../../../apps/desktop/node_modules/@earendil-works/pi-coding-agent/examples/extensions/gondolin/index.ts)). The SSH example overrides only four ([`ssh.ts`](../../../apps/desktop/node_modules/@earendil-works/pi-coding-agent/examples/extensions/ssh.ts)). Caution from pi: "Extensions run wherever the `pi` process runs … other custom extension tools still run on the host unless they also delegate their operations" (containerization).
- **Whole process inside:** "Plain Docker … Provider API keys enter the container"; OpenShell "providers can keep raw model API keys outside the sandbox … code inside the sandbox can call `https://inference.local`, and the gateway injects the configured provider credentials upstream"; Docker Sandboxes "receives a sentinel value … the `sbx` proxy substitutes the real credential on egress" (containerization). With a remote OpenShell gateway "project files are not bind-mounted from the host" so the repo must be cloned or uploaded (same page).
- **Headless protocol already exists.** `pi --mode rpc` is JSONL over stdio with `prompt`, `steer` ("delivered after the current assistant turn finishes executing its tool calls, before the next LLM call"), `follow_up`, `abort`, `clear_queue`, `get_messages` ([rpc](../../../apps/desktop/node_modules/@earendil-works/pi-coding-agent/docs/rpc.md)).
- No in-process sandbox: pi's security doc says real isolation "needs to come from the operating system or a virtualization/container boundary" ([security](../../../apps/desktop/node_modules/@earendil-works/pi-coding-agent/docs/security.md)).

## Cross-cutting findings

1. **Both halves of the fork are normal products now, and they converge on the same "customer worker" shape.** Anthropic self-hosted sandboxes and Cursor Self-Hosted Machines are: outbound-only HTTPS from a worker, a work queue ("Chats wait in the team pool until a worker claims them"; "Your worker claims the work item"), lease heartbeat, `stopping`/`stopped`, a stale-worker metric (`workers_polling`, `pending`), and a loop that stays in the vendor cloud ([self-hosted sandboxes](https://platform.claude.com/docs/en/managed-agents/self-hosted-sandboxes), [operations](https://platform.claude.com/docs/en/managed-agents/self-hosted-sandboxes-operations), [Cursor self-hosted](https://cursor.com/docs/cloud-agent/self-hosted)). That is the superseded ADR 0012 almost word for word; the vendors needed it because their loop is not on the worker.
2. **Keeping the loop with the sandbox was found expensive by the people who tried it first.** Anthropic: all components in one container made it a pet, made failures indistinguishable, put credentials next to generated code, and forced customers to peer their VPC; p50 time-to-first-token fell about 60% and p95 over 90% once the brain stopped waiting for a container ([engineering post](https://www.anthropic.com/engineering/managed-agents)). OpenHands V1 went the other way (agent and tools together) because separate processes drifted and mandatory isolation broke MCP's local-execution assumption ([design](https://docs.openhands.dev/sdk/arch/design)). Two good teams, opposite lessons; the difference is whether you own a multi-tenant fleet.
3. **Credentials: the structure is "placeholder inside, substitution outside".** Codex network secrets, Claude's GitHub proxy and API credentials, Docker `sbx` sentinel, OpenShell `inference.local`, Cursor OIDC all do this. Where vendors fall short they say so: Cursor Runtime Secrets are still env vars a human can read; Claude's API credentials are Pro/Max only; Codex's legacy "delete before agent phase" breaks tools that need a credential at run time.
4. **Git exit is deliberately narrow.** Single branch, no tag, no delete, draft PR, human approves workflows and merges, commit signed and linked back to the session (Copilot, Cursor, Claude). Claude's proxy admits it "doesn't limit which branches a push can update" and defers to branch protection.
5. **Environment = a snapshot built from a setup script, with expiry.** Claude ~5-minute cache budget and ~7-day rebuild; Codex 7-day state; Cursor 90-day snapshots; Devin one snapshot per org per platform; Copilot re-runs an Actions workflow each time with a 59-minute ceiling. The definition is held in the vendor UI (Codex, Claude, Devin), a Dockerfile in-repo (Cursor), or an Actions workflow in-repo (Copilot). **None of the primary docs I read use `devcontainer.json` as the cloud environment definition** (Codex's devcontainer example is for local use). Treat "devcontainer" as **UNVERIFIED** as a vendor pattern.
6. **Network default is the main safety dial, and it is a tradeoff openly stated.** Codex legacy: off, with method restriction; Claude: Trusted allowlist; Copilot: firewall; Cursor: on by default, restrictable. Every vendor except Devin names prompt injection plus exfiltration as the risk of turning it on.
7. **Everything resumable keeps the log apart from the sandbox, and the log has a sequence.** Anthropic (`getEvents` positional slices, dedupe by id), OpenCode v2 (aggregate `seq`, `after` cursor, tail without a race), Codex relay (`seq`/`ack`/`resume`), Cursor (conversation vs snapshot retention). Live deltas are a UI nicety only.
8. **Triggering identity is the billing and permission identity.** Codex: "the account of the issue creator"; Cursor: inherited access, never widened; Copilot: write access required, requester can't approve; Claude: your account's rate limits. Shared environments share *requirements*, not credentials (Codex personal vault).

## Implications for Kira

### Constraints from the ADRs

- **0003/0006:** the desktop never holds a provider key; the Kira key is per device, 90-day, and a 401/403 deletes it and signs the user out.
- **0005/0028:** one allowance, one per-person cap on simultaneous completions (`MAX_CONCURRENT_COMPLETIONS_PER_PERSON = 5`, in-memory in `pool.ts`) that counts a chat's subagents.
- **0012 (superseded by 0024):** "a run spends its payer's allowance, so the hand that starts it should be theirs"; only the payer steers; revisit "if a remote sandbox ever exists". 0024 removed claims, leases and workers; a ticket is Running until a person changes it; the PR is the review; each ticket is its own branch.
- **0026/0029/0030:** the server already mints GitHub App installation tokens live and watches PRs and checks by webhook; a repository is attached *from a checkout*, so a folder with no remote has no clone source.
- **0028:** "nothing outlives the app"; the app-level registry was rejected because "Kira has no server to host it in".

### Pick the placement first

| If the need is | Placement | Cost to Kira |
| --- | --- | --- |
| Isolation, parallel checkouts, heavy builds, untrusted repos, while the laptop stays on | **C: hands remote** (pi `*Operations`) | small; no new server state; key and transcript unchanged |
| The run keeps going when the laptop closes; steer from a phone | **A or B: loop leaves the desktop** | large: server-side transcript, headless pi host, per-run credential, new stream, revisit 0012/0024/0028 |
| Phone as a window onto a running desktop | **D plus relay** (already Kira's shape; add a relay like Codex Remote / Vibe Kanban / Copilot remote control) | medium: relay and client only, no brain move |

My recommendation: **build C first if "remote" means isolation; do not build A/B until someone actually needs the run to outlive the laptop.** The hands-remote path is the only one where Kira keeps all three properties it paid for (model key off the machine, transcript in SQLite via `_persist`, no server transcript store). Per Anthropic's post, hands-remote with the brain outside "called the container the way it called any other tool", so a dead sandbox is a tool error, not a lost chat. It does not deliver "runs while the laptop sleeps", which is the headline feature of Codex Cloud, Claude on the web, and Cursor Cloud Agents; D/C both die with the laptop.

### 1. pi `*Operations` (apps/desktop/node_modules/@earendil-works/pi-coding-agent/docs/extensions.md, "Remote Execution")

- The documented mechanism: re-register built-in tools with `createReadTool(cwd, { operations })`. Operations interfaces: Read, Write, Edit, Bash, PowerShell, Ls, Grep, Find. **Override all seven file/shell tools and `user_bash`.** The SSH example overrides four and leaves `grep`, `find`, `ls` reading the host disk, which silently defeats isolation; the Gondolin example is the complete reference.
- Kira's `kiraExtension` is already an `extensionFactories` entry in `agent.ts` that receives `cwd`, `getShellPath`, `role`, so an executor extension has a home. `Conversation.runShell`/`cancelShell` (user `!` commands) must route through the same executor or they run on the host.
- Kira's own tools (tracker, MCP, memory, questionnaires) run in the desktop process: correct for hands-remote, since they are brain-side and keep their credentials local. But anything in `kiraExtension` that reads `thread.cwd` directly (skills, `AGENTS.md`/project discovery by pi's resource loader, workbench file watching per ADR 0016, git status per ADR 0014) will look at the *local* folder. Whether a remote checkout is visible to the resource loader is **UNVERIFIED**; Gondolin sidesteps it by mounting the host cwd into the VM, which a remote sandbox cannot do (pi: with a remote OpenShell gateway "project files are not bind-mounted", clone or upload instead).
- Failure semantics to copy: translate transport loss into a tool error returned to the model (Anthropic), mark an interrupted in-flight tool "interrupted, never replayed" (OpenCode v2), and keep long-poll output cursors on the executor so a reconnect can `read after seq` (Codex `process/read`). Codex's executor kills processes when the connection closes; decide Kira's rule deliberately.
- Repo: with brain-local, the checkout can stay on the desktop and the executor can be a local micro-VM or container (Gondolin pattern) with **no network or credentials**, which is the cheapest isolation win before any remote machine exists.

### 2. The `Conversation` interface (apps/desktop/src/main/pi/conversations.ts)

- Its verbs already match every protocol surveyed: `send`/`followUp`/`steer`/`queued`/`takeQueuedBack`/`stop` correspond to Anthropic `user.message`/`user.interrupt`, Codex `turn/start|steer|interrupt`, OpenCode v2 `delivery: 'steer' | 'queue'` with a cancelable inbox, and pi RPC `prompt|steer|follow_up|clear_queue|abort`. `QueuedLine`'s `next`/`later` lanes (ADR 0012) are OpenCode's `steer`/`queue`. No new concepts are needed; the vocabulary is Kira's.
- **It is not remote-capable as written.** Reads are synchronous: `transcript()`, `queued()`, `isRunning()`, `modelId()`, `chatUsage()`, `streaming()`, `runningSince()`, `subagents()`, `memory()`, `conclusions()`. A `RemoteConversation` (OpenHands uses exactly this name for the same swap) would need them async or served from a client-side projection fed by an event stream. `close()` "dispose[s] the session"; for a remote chat the equivalent is detach, not stop.
- If hands-remote only (C): `Conversation` does not change at all. That is the strongest reason to start there.
- If the loop moves (A/B): add idempotent admission (caller-supplied message ID, OpenCode v2 style) so `send`/`steer` retries after a dropped request are safe; surface "queued but not yet processed" (Anthropic `processed_at: null`) because `takeQueuedBack` is only honest while the line is still unread; Claude Code web has the same ✕-until-read rule.
- Keep one rule from Codex: `turn/steer` carries `expectedTurnId`. Kira's `steer` should name the turn it thinks is running, or a steer that arrives after the turn ended starts something unintended.

### 3. `openChats.ts`

- Its job is to own *open vs shown* and keep a chat alive while writing; ADR 0028 extends "writing" to running children. A remote-brain chat has no local session to retain, so it needs a second entry kind ("attached", with a stream subscription, no `Conversation` session) and a different answer to "is Kira writing in this chat": ask the server. Archive/delete protection ("Kira is writing in this chat") must consult that same answer or a laptop can delete a chat an off-device run is still writing.
- ADR 0028 rejected app-level child ownership because Kira has no host for it. Pattern A/B is that host. Anthropic's sizing is the number to plan with: about 1 GiB RAM, 5 GiB disk, 1 CPU per agent, memory growing with session length ([hosting](https://code.claude.com/docs/en/agent-sdk/hosting)). The Bun server is currently a store plus a proxy, so this is a new class of load, not a feature.
- Pattern D needs nothing here; the chat is already retained while the desktop runs.

### 4. The server's `/v1` proxy and keys (apps/server/src/pool.ts, keys.ts, auth.ts)

- **Today one bearer does everything.** `keyHolder` is "the wall in front of anything that answers on a caller's behalf" for both the desktop routes and the model proxy; the key is the device's, 90-day, no scoping (`auth.ts`: `requireName`, `defaultExpiresIn`, rate limit off). Putting that key inside a sandbox (pattern A, or any whole-pi-in-container) gives generated code the user's ticket, memory and allowance authority until expiry. That is the precise failure Anthropic describes ("a prompt injection only had to convince Claude to read its own environment"). In pattern C the key never leaves the desktop; this problem does not exist.
- **If a sandbox must call `/v1`:** mint a **per-run key** and teach `keyHolder` to refuse it on every route except `/v1`. Better Auth supports what that needs: multiple `configId` configurations with their own prefix and permissions, per-key `expiresIn`, `remaining`, and `metadata` ([Better Auth API-key advanced](https://better-auth.com/docs/plugins/api-key/advanced)); today `keyHolder` calls `verifyApiKey({ key })` without checking `configId`, so the route check is new code. Alternative that matches pi's own guidance: an injecting egress (OpenShell `inference.local`, Docker `sbx` sentinel substitution), so the sandbox holds a sentinel and never a Kira key.
- **ADR 0006's 401 rule must not apply to a run key.** Today a 401/403 on the device key deletes it and signs the person out; a run key expiring mid-run must end the run, not the session. Choose run-key lifetime against expected run length (Copilot caps at 59 min; Claude's cache budget is ~5 min of setup).
- **The cap becomes the parallelism limit.** `activeByUser` allows 5 simultaneous completions per person, in memory, and counts a person's whole fan-out (ADR 0028). Parallel remote runs (every vendor's headline feature) will hit it with one person's four runs plus their own chat; the refusal text says "You already have 5 model requests running", which will read wrongly for a run nobody is watching. Decide whether runs share or get their own bucket before building.
- **Attribution gap.** The `usage` ledger row has user, model, tokens, outcome, reason, time. No thread, ticket or run column (`schema.ts`). Every vendor bills per triggering user, which Kira already does, but "what did FND-12 cost" is unanswerable. Add a run/thread identifier at the key (metadata) or header.
- **Billing stays with the person who starts it.** Codex (issue creator's account), Cursor (spend limit per user), Copilot (premium request per session to the requester) all match ADR 0012's "the hand that starts it should be theirs". Do not build delegated billing for delegated runs; `agent assigned a ticket by someone else` is where all three vendors had to add explicit rules (requester cannot approve; non-writers ignored).

### 5. Transcript: Kira has no server-side store, and it is the load-bearing question

- Hands-remote and device-relay keep it that way. Anything that lets a run outlive the laptop needs an append-only entry log on the server, keyed by thread and sequence, written by the brain and read with an `after` cursor. Reasons from the sources: Anthropic's "the session is not Claude's context window", durable and queryable; Agent SDK hosting says transcripts on container disk are lost and that for the hybrid pattern the `SessionStore` "is required … not optional"; OpenCode v2's cursor is one durable aggregate sequence.
- **pi's session already is an append-only tree of entries**, and Kira already intercepts every write: `storage.ts` overrides `_persist` to send entries to `ThreadStore`. A remote brain would swap `_persist` for a server append. Claude's SDK does the same as a dual-write mirror and says the mirror is best-effort; for Kira the server copy would be the record, so the write must be acknowledged, not best-effort.
- ADR 0012 originally said "Its transcript belongs to the project … crosses to the server"; ADR 0024 dropped it ("a chat is its transcript"; per-run record goes). A server log would partly undo that and hits ADR 0009 (readable by project members) and the vendors' retention questions: Cursor keeps conversations indefinitely and snapshots 90 days; Managed Agents is not eligible for ZDR/HIPAA *because* it stores sessions. Decide retention and deletion (`Delete Agent API`-style) before the first row is written.
- Kira has no realtime channel (ADR 0026: "the Work surface refetches on `updatedAt`"). Every vendor uses a stream plus history list. A server stream for an off-device run is new infrastructure; SSE with list-then-tail-and-dedupe (Anthropic) or an `after` cursor (OpenCode v2) is the documented shape. Token deltas should be optional and never advance the cursor.

### 6. Repo in, changes out

- The server already has the pieces vendors use: GitHub App installation tokens minted live and a webhook that moves Needs review to Done on merge (ADR 0026). The vendor pattern for a remote loop is: clone with a scoped credential, push one branch, open a **draft** PR, human merges, link back to the session in the commit trailer and PR body (Claude, Cursor, Copilot).
- Kira's rule (ADR 0024, 0026) already matches: one branch per ticket, PR is the review. Keep Copilot's extras in mind: sign commits, restrict to one branch, let branch protection do the real enforcement because even Claude's proxy "doesn't limit which branches a push can update".
- Scoping a GitHub App token to a single repository and fewer permissions is something I believe GitHub supports; I did not verify it in this note (**UNVERIFIED**). Do not hand the sandbox the installation token; follow Claude's GitHub proxy or Anthropic's "wire the token into the git remote at clone time and keep it out of env".
- ADR 0029's consequence bites: a project with no attached repository (nobody cloned it) or a folder with no remote has nothing to clone. Claude's answer is a git bundle upload (<100 MB, uncommitted tracked changes, secrets files excluded). For Kira the honest first rule is "remote runs need an attached repository", with bundle upload as a later, separate decision.

### 7. Tickets and runs (ADR 0024)

- No new entity. Codex, Copilot and Cursor all map one task to one session to one branch to one PR, and a follow-up on the ticket continues the *same* chat. Kira already has a ticket carrying linked chats; a remote chat is one more linked chat, and "Running" is still a stored status a person or the agent sets.
- Do **not** revive claims/leases/workers just because the vendors have them. They exist there because the loop is in the vendor cloud and the worker is a separate fleet. If Kira only does C or D there is no worker to lease. If a headless worker is ever built (B), the survey shows what it needs and it matches the superseded ADR 0012: outbound-only polling, work item states, lease heartbeat, graceful stop with a 30 s drain, a liveness metric.
- Parallel runs on one project: every vendor gives each its own sandbox/worktree/branch (Vibe Kanban: worktree per attempt, ephemeral). ADR 0024 accepted "two running tickets share one checkout" and said to revisit when it is a real complaint. A remote sandbox *is* the isolation, so the complaint disappears for remote runs only; local runs keep the old rule.
- Who may steer: Cursor makes shared agents read-only unless an admin enables follow-ups; Codex says another participant's Slack request does not continue your task. That is ADR 0012's "only the payer starts and steers", independently re-derived. Keep it.

### 8. Environment setup and network policy

- Kira's `prepareWorkspace` (`WorkspacePreparer`) is the existing hook. For a remote executor the vendor lesson is: setup runs once, is snapshotted, new tasks start from the snapshot, existing tasks keep their own state, and "saved state doesn't replace source control" (Codex). Cap setup time (Claude ~5 min or no cache) and make setup failure non-fatal where Copilot does (continue with current state) but visible.
- Defaults: no network or a package-manager allowlist; GET/HEAD/OPTIONS-only is available as a hard prompt-injection guard (Codex legacy); allowlist exact hosts, never wildcard buckets (Cursor). The model endpoint (`/v1`) must be reachable even at "no network" (Claude's "None" still reaches the Anthropic API, which the docs flag as a possible exfil path).
- Definition location: in-repo and versioned wins when you want review (Copilot's workflow, Cursor's Dockerfile); vendor-UI config wins for secrets. Kira already stores project skills on the server (ADR 0027); an environment definition fits the same store, but I found no vendor that uses `devcontainer.json`, so this is a design choice, not prior art.

### What not to copy

- Cursor "Runtime Secrets" (env var plus redaction) as a security boundary; their docs say a human in the terminal still sees them.
- Codex's legacy "delete secrets before the agent phase"; it broke run-time credential use and was replaced by proxy substitution.
- Mandatory sandboxing for every tool call (OpenHands V0's lesson).
- Vibe Kanban's product as a base: its README announces it is sunsetting.

### Open question

Does a Kira run need to **keep going after the laptop closes**? If no, build C: route pi's seven tools and `user_bash` through an executor in a no-credentials VM or container at `kiraExtension`, leave `Conversation`, `openChats`, the keys and the transcript alone. If yes, this note is the checklist for what has to move (loop host, transcript log, per-run key, stream, cap policy) and it is a new ADR, not a change to 0028.
