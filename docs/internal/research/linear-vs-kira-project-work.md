# Linear vs Kira Project Work

**Research date:** 2026-09-25  
**Scope:** Compare Linear's documented product model with the current Kira Project Work implementation and ADRs in this repository. Linear facts below use first-party Linear documentation. Kira facts use the current repository snapshot and are cited by path and line range. “Unknown” means the inspected sources do not establish the behavior, not that the product cannot support it.

## Executive summary

Linear is a mature, configurable work-management system organized around **workspaces → teams → issues**, with projects and initiatives above issues, cycles for team planning, rich collaboration, permissions, integrations, webhooks, and built-in or installed AI agents. Kira Project Work is a narrower, server-held work queue organized around **projects → tickets**, with derived readiness, one blocking relation, person-owned claims, desktop-local runs, project glossary and approved decisions.

The closest conceptual overlap is Linear issues/projects versus Kira tickets/projects. The main difference is ownership of workflow and execution: Linear exposes configurable human workflow states and assignments, while Kira derives queue bands from gates, blockers, claims, runs, and verdicts, then executes agent runs on a user's desktop. Kira's current implementation has no confirmed cycles, initiatives, project updates, general documents, fine-grained permissions, or external integration/webhook surface comparable to Linear.

## Confirmed versus unknown

### Confirmed in Kira

- Server-side Projects and project-scoped Tickets are implemented with typed routes and Postgres schema.
- Ticket kinds, criteria, gates, rank, closure, blockers, claims, runs, transcripts, outcomes, Decisions, and glossary history are represented in the current code.
- Queue bands are derived rather than freely edited.
- Runs execute on a user's desktop worker, use claims/heartbeats, and remain human-approved proposals.
- Project glossary and Decisions are server-held, not repository files.
- Current authorization is authenticated access; the inspected code does not show Linear-like team/guest/private-project permissions.

### Unknown or not confirmed in the current Kira snapshot

- Cycles, iterations, milestones, initiatives, project health/status updates, general collaborative documents, labels, estimates, saved views, comments as a general work surface, or a public webhook/integration directory.
- A first-class project-to-repository mapping. ADR 0010 explicitly records that projects carry no repositories yet and identifies provisioning as future work. [`docs/adr/0010-work-is-tracked-against-a-project.md:67-72`](../../adr/0010-work-is-tracked-against-a-project.md)
- Autonomous queue dispatch or delegation to another person's worker. The ADR explicitly says the person starts the run and delegation is not built. [`docs/adr/0012-a-run-happens-on-a-desktop.md:28-34`](../../adr/0012-a-run-happens-on-a-desktop.md)
- Whether all planned ADR behavior is fully shipped in every renderer path. This report treats code and ADRs separately and does not infer implementation solely from design text.

## Research limitations

- Linear documentation is first-party but mutable; this is a point-in-time comparison accessed on 2026-09-25, not a historical snapshot or exhaustive changelog audit.
- No Linear workspace was inspected, so plan-dependent availability, tenant configuration, and undocumented behavior remain unknown.
- Kira evidence is limited to the checked-out repository and its ADRs. “Not found” means not found in the inspected current Project Work sources, not proof that no unrelated prototype exists elsewhere.
- Repository links are local evidence rather than externally browsable URLs. Line ranges identify the exact checked-out source used for Kira claims.
